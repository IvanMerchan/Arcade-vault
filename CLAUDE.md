## Project

Arcade Vault — a retro-themed arcade portal (Spanish UI, see README.md): a catalog of 8 games, a global leaderboard, and 2 actually-playable games. Built via spec-driven development; `specs/01` through `specs/07` are all `Implementado`.

Route map:

| Route                  | File                               | What it does                                          |
| ---------------------- | ---------------------------------- | ----------------------------------------------------- |
| `/`                    | `app/page.tsx`                     | Home landing → `components/Home.tsx`                  |
| `/biblioteca`          | `app/biblioteca/page.tsx`          | Filterable catalog → `LibraryScreen` + `GameCard`     |
| `/juegos/[id]`         | `app/juegos/[id]/page.tsx`         | Game detail + top 10 scores (Server Component)        |
| `/jugar/[id]`          | `app/jugar/[id]/page.tsx`          | `PlayerScreen` — HUD + the game canvas                |
| `/salon`               | `app/salon/page.tsx`               | Hall of fame → `HallOfFame`, top 12 per game          |
| `/auth`                | `app/auth/page.tsx`                | Simulated login (localStorage only, no Supabase Auth) |
| `/api/supabase-health` | `app/api/supabase-health/route.ts` | Connection health check (SPEC 03)                     |

Both `[id]` routes use `generateStaticParams`; every route has its own `loading.tsx`; `app/not-found.tsx` is a themed 404.

## Data architecture

- **Reads** happen only from Server Components via `lib/queries.ts`: `getGames`, `getGameById`, `getGameIds`, `getTopScores`, `getAllTopScores`. No component talks to Supabase directly.
- **Clients**: `lib/supabase/server.ts` exports `createClient()` (cookie-aware, request-time) and `createStaticClient()` (no cookies, used from `generateStaticParams` at build time, where `next/headers` cookies() would throw); `lib/supabase/client.ts` is the browser client.
- **Writes**: the only write path is `SessionProvider.saveScore()` (`components/SessionProvider.tsx`), an anonymous insert into `scores` from the browser.
- **Schema** (`supabase/migrations/`): `games` (catalog rows with `sort_order`, CHECK constraints on `cat`/`color`), `scores` (`game_id`, `player_name` 1–10 chars, `score` 0–10,000,000), and a `game_stats` view (`best`, `plays`, created with `security_invoker = true`). RLS: public SELECT on both tables, public INSERT on `scores`. No auth yet — an accepted, documented risk (see SPEC 06).
- Invariants an agent could otherwise break without noticing:
  - Never reintroduce a hardcoded `GAMES` array in `lib/games.ts` — SPEC 05 removed it on purpose. The `games` table is the single source of truth; `lib/games.ts` now only holds types, `formatScoreDate`, and `CATS`.
  - `best`/`plays` are never columns — they're always derived from the `game_stats` view.
  - The leaderboard is already generic over `game_id`. Adding a new game never requires new leaderboard code.
  - Every schema change ships as a versioned file in `supabase/migrations/NNNN_*.sql` **and** gets applied via `mcp__supabase__apply_migration` — never applied through MCP alone, or the git history loses it.

## Playable games

`lib/game-registry.ts` maps a `game.id` to a real playable component; today `isPlayable()` covers `{"asteroides", "caida"}`. `components/PlayerScreen.tsx` statically imports `AsteroidsGame` and `TetrisGame` and falls back to a mock arena (`setInterval`-driven score) for the other 6 catalog entries.

Contract every playable component implements: `{ running, onStats, onGameOver, skin }` (`PlayableGameProps` in `lib/game-registry.ts`). `running = !paused && !over`; going `false` cancels the `requestAnimationFrame` loop and removes the keyboard listeners — that's what lets the "TUS INICIALES" input capture arrow keys after game over. `skin: GameSkin` (`lib/game-skins.ts`) carries the active visual theme (`clasico`/`neon`/`retro`); it's mirrored into a `useRef` like `onStats`/`onGameOver` and must never join the effect's dependency array or `PlayerScreen`'s `key={playId}` — changing it must not restart the loop or the game. `PlayerScreen` owns the selection and persists it globally in `localStorage` (`arcade-vault:skin`).

Rules for a new game component: `"use client"`; all mutable state in a single `useRef`, never `useState` (avoids re-renders at 60fps); `onStats` fires only when a value actually changed; `onGameOver` fires once per playthrough; fixed internal canvas resolution 800×600 (4:3, matching `.crt-screen`); the component draws neither its own HUD nor its own game-over overlay — that's `PlayerScreen`'s job.

Detailed reference: `.claude/skills/add-game/porting-guide.md`. Portable sources live in `references/started-games/` (`02-asteroids` and `03-tetris` already ported; `04-arkanoid` not yet).

**Before answering which games exist, which are already playable, which are still mock-only, or before starting work to implement a new one, check `references/implemented-games.md` first.** It lists the full catalog plus which ids have a real playable component (see table above) — anything not in that "jugables" list is still mock and a candidate for `/add-game`. It's a snapshot and goes stale the moment a game is added or the catalog changes, so re-query the DB (`mcp__supabase__execute_sql` / `list_tables` on `games` + `game_stats`) instead of trusting it blindly whenever the answer needs to be current — and update the file after any change to the catalog or to `isPlayable()`.

## Skills

Always use `/frontend-design` when designing or reshaping UI.

`/spec` and `/spec-impl` are installed (`.claude/skills/`, mirrored in `.agents/skills/`, pinned in `skills-lock.json` from `Klerith/fernando-skills`) — spec-driven development is active, not just intended.

`/add-game` (local, `.claude/skills/add-game/`) designs the spec for wiring up a new playable game + its leaderboard. It only writes `specs/NN-slug.md`, never app code.

The `game-planner` subagent (`.claude/agents/game-planner.md`) decides _which_ game to implement next — it ranks catalog mocks, portable sources in `references/started-games/`, and net-new ideas against the platform's fit criteria, and remembers past rounds in `references/game-suggestions.md` / `references/game-suggestions-todo.md` so it never re-proposes something already `Implementado`. It hands its pick to `/add-game`; it never writes specs or app code itself.

The `game-jam` subagent (`.claude/agents/game-jam.md`) turns a creative theme into a full spec package instead of ranking the existing catalog — given a theme, it proposes 3 mechanically distinct concepts, lets the user pick one via `AskUserQuestion`, and writes 3 specs (`gameplay` / `integracion` / `pulido`) into `specs/game-jam/<game-id>/`, all `Borrador`. It reads `references/game-suggestions*.md` only to avoid duplicate ids/concepts — it never writes to them, never touches the numbered `specs/*.md` sequence, and never writes app code.

The `skin-designer` subagent (`.claude/agents/skin-designer.md`) is the exception to the "agents never write app code" rule — it audits every playable game against the 3-skin requirement (`clasico`/`neon`/`retro`, see above) and, when one is missing or partial, implements it directly in `lib/game-skins.ts` and `components/*Game.tsx` **for exactly one game per run** — whichever the user names explicitly, never all of them in one pass — validating legibility with a WCAG contrast check against `--bg` (the app is dark-only, no light mode). Its memory lives in `references/game-with-themes.md`. Scope is limited to games with a real draw component — the 6 mock catalog entries are out of reach until they get one.

The `mobile-porter` subagent (`.claude/agents/mobile-porter.md`) is the other exception to that rule — it audits `/`, `/biblioteca`, `/juegos/[id]`, `/salon`, and `/auth` (the 5 routes SPEC 08 left explicitly out of scope) against a mobile checklist (no horizontal scroll, ≥44px touch targets, readable type, nothing broken under a ~390px viewport), using SPEC 08's own patterns (`@media (pointer: coarse)`, the global `viewport` export in `app/layout.tsx`, additive `@media` blocks) as its technical reference. When a route fails the checklist it fixes it directly in `app/globals.css` and that route's component, **for exactly one route per run**, and it never touches `/jugar/[id]` — that scope stays with SPEC 08. Its memory lives in `references/mobile-audit.md`.

## Spec Driven Design

Workflow in practice: `/spec` (or `/add-game`) writes `specs/NN-slug.md` in `Borrador` status → user approves it → `/spec-impl NN-slug` creates branch `spec-NN-slug` (`AutoCreateBranch: true` in `specs/.spec-config.yml`) → PR into `main` → spec flips to `Implementado`. Spec convention (see `specs/01`–`07`): section headers in English, body in Spanish, header block with `Status` / `Depends on` / `Date` / `Objective`.
